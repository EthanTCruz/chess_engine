# Journey so far
## Project Goal:
### Develop an evaluation algorithim using neural networks for determining the strength of a chess position using past games data. This algorithim should also be able to generalize beyond the dataset and be applied to new positions and as a part of a chess engine.
## Phase 1
This iteration involved Tensorflow, SQLite, CSV's and was centered around using 60+ handcrafted evaluation metrics per position such as castling rights, center pawn control, piece amounts, etc. and was labeled as  either white win or black win for the win/strength probabilities. Eventually this was proved very inneffective as the process and number of possible handcraftable evaluation metrics was far too large to ever concieve of them all at once. There were also issues with identifying drawish positions and a large bias for white to win as in the dataset they won around 70% of the time. SQLite was utilized for storing unique attributes of each position, such as piece locations, castling rights, what color won the game, etc. then by grouping by these characteristics and summing the color win amounts of the positions a dataset was built showing the 'win buckets' of white or black from the given position. The data was then written to CSV from SQLite for use by Tensorflow as SQLite DB's are not very efficient with massive and rapid amounts of read requests.

## Phase 2
This iteration involved Pytorch, SQLite, MongoDB and was centered around using bitboards, the 8x8 bit representation of a given piece type. The idea was by using image recognition principles like pattern recognition and edge detection, handcrafted evaluation metrics would no longer need to be created as algorithim would be able to calculate such things from its own interpretation of the bitboards. This also saw the addition of stalemate as an attribute to the 'win buckets' characteristics to help assist in the self play portion of training so as to hopefully avoid drawish positions by using it as a minimized value when selecting favorable positions. The switch to PyTorch was to mirror research environments where PyTorch seems to have earned more favorability. SQLite was used the same as before, but MongoDB was now used in place of CSV's for storing the aggregated positional data. The switch to MongoDB inspired by the need for an efficent database with an everchanging and very flexible schema for the storage of several different types of bitboards. MongoDB proved to be very efficient, the only draw back was it required a separate container in order to operate the chess engine which made things more complex than they needed to be, this is why it was exchanged for H5PY in the next phase.

## Phase 3 
this iteration involved PyTorch, SQLite, H5PY and was inspired by the DeepChess paper's approach to flattening bitboards and other board position data for use with an autoencoder to shrink all the given chess data to just 100 neurons. From these 100 neurons a much smaller space is used as input into a deep learning network for interpreting the favorability of a position. The large differences between this implementation and DeepChess's implementation is we only use a single position as input into the deep learning network, and we return the position's favorability instead of the stronger positon between the inputs. Additionally this new implementation leverages PyTorch dataloaders more effectively and about 50+ million more records of data.
